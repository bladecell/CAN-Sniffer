# Decisions

Decisions that shape the code, and why. Add one when an open decision (`D#` in the plan) is made, or when a design choice would surprise someone reading the code.

Format: `## <date>: <decision>`, then context, the choice, and the alternatives that were rejected.

## 2026-10-10: Agent docs live in `docs/`, planning in a gitignored `plan/`
Code layout is found by reading the code, so there is no separate codemap. `docs/` holds what the code can't tell you: contracts, formats, state machines, hardware and decisions.

## 2026-10-10: HW revision is a Kconfig choice that includes v1.1
`main/Kconfig.projbuild` offers V1_1, V1_2 (default) and V2. The task text names only V1_2 and V2, but v1.1 boards exist and run the same firmware, so dropping its pin set would break them. V2 has no pin set; selecting it is a build `#error`, not invented pins.

## 2026-10-10: Partition table and sdkconfig baseline (P0.7)
16 MB flash: `ota_0` and `ota_1` are 2 MB each (the app is 1.2 MB), `www` 1 MB, `coredump` 256 KB, laid out once so OTA-3 needs no table change. `sdkconfig.defaults` is the config source of truth, generated from the previous `sdkconfig` with `idf.py save-defconfig`, plus the P0.7 debug options. `PANIC_PRINT_HALT` was replaced by `PANIC_PRINT_REBOOT`: an unattended device must reboot, not halt.

## 2026-10-10: Static analysis setup (P0.2)
`tools/clang-tidy.sh` runs `run-clang-tidy` from esp-clang itself instead of `idf.py clang-check`. pyclang 0.6.3 leaves `-mdisable-hardware-atomics` in the command line, clang rejects it and skips those files, and its default `-checks=` would override `.clang-tidy`. cppcheck runs with `-D__cplusplus=201703L` because 2.17 cannot preprocess IDF's `__VA_OPT__` log macros. Vendored `tinyexpr` is excluded from clang-tidy and cppcheck, and builds with `-Wno-array-bounds` (known GCC false positive on its allocation trick) but otherwise `-Wall -Wextra -Werror`.

## 2026-10-10: v1.1 stays in the HW choice; v2 is an `#error` by design
Decided by the user. `CONFIG_SNIFFER_HW_REV_V2` exists so the choice is complete, but selecting it fails the build with a clear `#error` until the v2 pin map is known. No guessed pins.

## 2026-10-10: cert-err33-c is on
Write paths check `fflush`, `fsync` and `fclose` and return `ESP_FAIL` (`SDCard::write_file`, `create_file`). Read-only `fclose` and sized `snprintf` are cast to `(void)` with the reason in a comment where it isn't obvious.

## 2026-10-10: Parsing code lives in hardware-free files, tested on the host
`obd2_frame.cpp` (single frame, ISO-TP first and consecutive frames, DTC and VIN extraction) and `pid_json.cpp` (PID JSON) hold the logic the OBD2 class and the middleware used to inline. The OBD2 class calls them; host tests (`test/host/`) cover them without CAN hardware. Reassembled ISO-TP payloads are capped at 512 bytes, and `CONFIG_CJSON_NESTING_LIMIT` is 32 (the default 1000 overflowed a small task stack in a host test).


## 2026-10-11: The SD card is never formatted automatically
Decided by the user. `format_if_mount_failed` is false. A corrupt or foreign card stays untouched and is reported as not mounted; formatting happens only through `POST /api/v1/sd_card/format`. A boot without a card keeps running with no default PID set (B1 stays a no-card limitation by choice).

## 2026-10-11: v2 overlay, size numbers and coredump fit (R3, R5, R6)
`sdkconfig.defaults.v2` layers v2 flash, PSRAM and partitions over the v1 defaults. R5 (v1-pin scratch build with v2 keys): app 1205600 B with PERF, 1101328 B with SIZE (-8.6%); default stays PERF, not changed. R6 (estimate, no forced panic): the ELF dump stores each task's used stack (SP to top), TCB and registers, not the whole 8K. About 22 tasks (6 async workers of 8K, httpd 8K, OBD2 poll and receive 8K, main 8K, ...) total about 127K of stack if dumped whole, which would not fit 64K. By the measured high-water marks the used stacks sum to about 40K, plus about 0.7K per task of headers: about 55K, against a 50 KB dump measured at P0.7. It fits with thin margin and not with a guarantee; a dump that does not fit is dropped, not a crash. `CONFIG_ESP_COREDUMP_STACK_SIZE` is the handler's own stack, not a cap. `CONFIG_ESP_COREDUMP_DATA_FORMAT_BIN` still dumps the same stacks, so it only trims header overhead (unmeasured) and loses ELF/GDB tooling. Real levers: fewer async workers (6 to 3 saves about 11K) or `ESP_COREDUMP_MAX_TASKS_NUM`.

## 2026-10-12: One name `autoPoll`, RAM only; recovery by VIN match (B31)
`continuousRunning`, `startContinuousMode` and `pid_poll?running=` are replaced by `autoPoll` everywhere (`setAutoPoll`, `m_auto_poll_set`, `POST /api/v1/req/auto_poll?auto_poll=`, `auto_poll` and derived `polling` in `GET /api/v1/obd2`). No aliases. `autoPoll` is not persisted: it is the user's intent, set by the API and cleared by OBD2 deinit, so a sleep wake does not poll by itself. A health failure or bus drop never changes it. On CAN reconnect with `autoPoll` set the VIN is read; the same VIN as the last completed discovery skips supported-PID discovery (the known VIN lives in RAM, is set only after a completed discovery on the autoPoll path, survives a bus drop, is wiped by deinit and by any discovery run), otherwise discovery runs with 2 s to 30 s backoff. After a health-check queue clear the queue is restored on the first successful probe, without rediscovery.

## 2026-10-12: A successful user VIN read is a recovery trigger (B31)
A successful VIN request (`POST /api/v1/req/vin` or the supervisor's connect-time read; `GET /vin` only reads RAM) proves the ECU answers, provided the VIN is exactly 17 ASCII uppercase letters or digits (`isValidVin`); anything else counts as a failed read. If OBD is not initialised it runs the connect decision (same VIN as the last discovery: restore the supported list; otherwise discover). If initialised, a different VIN rediscovers and a missing known VIN is adopted. It refills the queue only when `autoPoll` is already set and never turns it on. Discovery runs on the callback task, not in the HTTP handler, so the handler's latency is unchanged; the take of `discoveryMtx_` is non-blocking. Retries stay unbounded with the 30 s cap while `autoPoll` is set; a VIN-triggered rediscovery with `autoPoll` clear gets one attempt.

## 2026-10-13: Frontend size, DTC clear token, validation (F1 to F3)
Decided by the user. The frontend drops the latin-ext font, re-compresses `index.html.gz` with 7-Zip (zlib fallback) and drops unused dependencies; no size target (the `www` slot has about 520 KB spare). `POST /api/v1/req/clear_dtc` needs a one-shot confirm token from the firmware (first call returns 409 with a token, the second call carries it); the UI shows a confirm dialog between the two. Runtime validation of API and WebSocket data uses hand-written guards, no schema library; the frontend tests run with `bun test`. A null `minValue`/`maxValue` (cJSON writes NaN as null) is handled in the frontend, not by changing the firmware. The PID stream start/stop is ref-counted in `canStore`. The JS formula check in the PID editor stays for instant feedback; the firmware remains the final validator through the `POST /pid_def` errors. Later: `noUncheckedIndexedAccess`, removing dead components.

## 2026-10-15: Car battery card reuses the `battery` card type (F6)
The `battery` type was an unbuilt placeholder ("Battery Monitor"), so it now is the car battery card. Adding a second type would leave a dead placeholder. Saved `battery` items load: unknown modes (the old `default`) become `glyph`. The card reads `canStore.wsCanStatus` only; its history is a separate bounded buffer (`carBatteryFeed.svelte.ts`) sampled once per 0x03 frame, outside canStore. Staleness uses the local clock, because frame 0x03 carries no time. No data (no chart sample, no fill) when the bus is down, the WebSocket is down, the frame is older than 3 s, or the voltage is not a number, is 0, is above 20 V or is below 5.0 V (ADC floating or sensor fault).

## 2026-10-16: Settings array saves remain per item (B48 clarification)
Decided by the user. A CAN item with an invalid queue size saves nothing for that item. Other valid items in the same settings array may still be saved, even when the request returns an error. Keep the existing per-item processing; request-wide rollback is not added. The API documentation now states this explicitly.

## 2026-10-15: CAN driver review fixes: queue limits, simulator shutdown (B48, B49, B50)
Decided by the user. `rx_queue_size` must be 1..256 and `tx_queue_depth` 1..64. Out-of-range values are rejected, not clamped: `CanDriver::bringUp()` returns `ESP_ERR_INVALID_ARG` before any allocation, `POST` settings returns 400 and saves nothing, and a bad value read from NVS falls back to the defaults (20/20) so the device still boots. The simulator stop and start functions return a bool. If the simulator cannot stop, `teardown()` returns `ESP_ERR_TIMEOUT` and frees no queue; if it cannot start, `bringUp()` fails and rolls back. Deferred: admission counter for `transmit()`/`receive()` against `deinit()` (not reachable today, the Supervisor stops OBD2 first) and a single-atomic TX-done hook (no effect today, OBD2 passes the same pointer both times). Left open: urgent Flow Control may miss the 33 ms N_Ar under TX queue congestion, because frames already in the TWAI queue cannot be overtaken. Measure on the bench or a car before adding any dedicated capacity or priority mechanism.

## 2026-10-15: CAN driver operation admission (B51), reverses the deferral of #3
Decided by the user: the recorder will be a second caller of `transmit`/`receive`, so the teardown race is addressed now. `OpGate` (`can_driver/include/op_gate.hpp`, one atomic word, no FreeRTOS) guards `transmit`, `transmitUrgent`, `receive`, `availableMessages`, `flushRxQueue`, `getStatus` and `quickCheckBus`. `teardown()` closes the gate and drains in-flight calls for up to 3 s before stopping the simulator or freeing anything; on timeout it returns `ESP_ERR_TIMEOUT` and frees nothing. `transmit` and `receive` clamp their timeout to 2 s so a blocked call cannot outlast the drain. Atomics rather than OBD2's mutex-and-counter, because the driver has ISR callbacks. Still deferred: single-atomic TX-done hook (#5). Still open: urgent Flow Control N_Ar (#4).

## 2026-10-16: TX-done hook is one consistent {fn, arg} pair (B52), reverses the deferral of #5
Decided by the user. `HookCell` (`can_driver/include/hook_cell.hpp`) holds two fixed slots and one atomic pointer to the current one; nothing is allocated. The TX-done ISR counts itself into the slot it read, re-checks the pointer, copies {fn, arg} and keeps the count until the callback returns; after 4 lost races it skips that one report and never blocks. `setTxDoneHook` fills the idle slot, publishes it with one store and waits up to 200 ms for readers of the old slot; it returns true only when no call on the old pair is still running, and the caller may free the old arg only then. OBD2 `init` fails and `deinit` returns `ESP_ERR_TIMEOUT` when it gets false. Commit 2c43d83 does not build alone (a lock-free `static_assert` fails with `-mdisable-hardware-atomics`); 798f19c fixes it.

## 2026-10-17: Migrate the firmware to ESP-IDF 6.1 (B54)
Decided by the user. The firmware builds on IDF 6.1.0 (GCC 15.2, Picolibc, `-std=gnu++26`), HW V1_1 sdkconfig regenerated from `sdkconfig.defaults` (16 MB, `partitions_v1.csv`). Source changes: `espressif__cjson` replaces the `json` component, explicit `tx_queue_priority`/`left_len` initialisers, value-initialised `esp_vfs_littlefs_conf_t`, renamed `WIFI_REASON_*`. Config differences kept on purpose: `CONFIG_FREERTOS_IN_IRAM=y` (6.1 defaults FreeRTOS to flash; the cache-safe TWAI ISR needs it in IRAM, as on 5.5), `INT_WDT` 800 ms (6.1 default with PSRAM, was 300), coredump checksum SHA256 (was CRC32; `ESP_COREDUMP_ENABLE` selects the ELF format and SHA256 in `espcoredump/Kconfig`, so `sdkconfig.defaults` no longer names them), `CONFIG_FATFS_USE_DYN_BUFFERS=y` (6.1 default, one FATFS instance; every `fopen`/`opendir` caller checks for null), Picolibc instead of newlib. `tools/clang-tidy.sh` drops the `@toolchain/cxxflags` response file and takes include dirs from gcc with it. App size 1,270,656 B, +4.6% over 1,214,503 B (60% of the 2 MB V1_1 slot, about 81% of the 1536K v2 slot). Board (V1_1, simulator, plain flash): free heap 8.65 MB at boot, 18.5 PID/s, poll task stack free 7196 B, receive task 6044 B, VIN and all-mode DTC 200, CAN queues 20/20, zero CAN errors, no panic or watchdog. Not yet verified: sleep/wake and OTA update/rollback on 6.1.

## 2026-10-18: Access control: admin PIN, session token, BOOT-button claim (B19)
Decided by the user after the P2.6/P2.7 reviews (`plan/reviews/`). The default AP stays open for now (no WPA2 password, no TLS); this is accepted residual risk: anyone who can sniff the radio reads the PIN and token. The PIN stops cross-site forgery, DNS rebinding and casual users, not a nearby attacker.
- **Claim:** the first PIN is set by `POST /auth/claim`, accepted only within 60 s after a GPIO0 (BOOT) press made after boot. Recovery (clear the PIN back to unclaimed) is the same button and ships with the claim. GPIO0 is a strapping pin: holding it at reset enters download mode, so the press must happen after boot. A new `button` component (own `.c`/`.h`, `init()`/`deinit()`, debounced, no busy loop) owns the GPIO.
- **PIN:** 6 digits, salted PBKDF2-HMAC-SHA256 in NVS, constant-time compare. Changing it needs the old PIN (`PUT /auth/pin`) and ends all sessions.
- **Session:** `Authorization: Bearer` header, token from the hardware RNG, RAM only, up to 4 sessions, 30 min idle and 12 h absolute expiry. No cookie. One global failed-login counter with exponential delay and `429` + `Retry-After`; it blocks login only, never existing sessions.
- **Open (no auth):** dashboard reads (`/system`, `/can_bus`, `/obd2`, `/vin`, `/dtc`, `/pid_def` and `/pid_data` GET, `/sd_card/info`), `/ws`, and the `/req/*` commands. **Gated:** settings, SD file tree/download/upload/delete/format/copy, `pid_def` writes/save/load, `system/reboot`, `copy_file`, later OTA. `clear_dtc` keeps its confirm token and is gated. (Superseded the same day: `clear_dtc` is gated only, no token; see the entry at the end of this file.)
- **Order of checks:** Host/Origin guard, then auth, then rate limit, then handler. The guard must run before claim and login, or a rebinding page could claim the device. One `requireAdmin` check that does not depend on the transport, so TLS can slot in later.
- **Follow-ups:** try WPA3-OWE on the open AP (already enabled in sdkconfig; client support unverified). GNSS position and trips must be gated on HW v2.

## 2026-10-18: Settings validation and NVS read errors (P2.9a, SET-1)
One hardware-free validator (`main/include/settings_validation.hpp`) serves `POST /settings`, the `Settings` setters and the NVS loaders. Values are rejected, never clamped. NVS read buffers (64 B Wi-Fi strings, 256 B paths) are larger than the write limits, so a stored string fits. Loaders default the failing key only (too long, wrong type, out of range) and no longer count that as corruption. `factoryReset()` runs only on `ESP_ERR_NVS_CORRUPT_KEY_PART`; other read errors use in-memory defaults for the boot. The CAN pin whitelist is derived from the ESP32-S3 pin map (docs/api.md) plus the board SD and LED pins from `utilities.h`; per-item persistence (2026-10-16) is unchanged.
Follow-up (2026-10-18): `lbk_pin` and `rs_pin` stay required, so -1 (GPIO_NUM_NC) is rejected: `CanDriver::bringUp` and `setDebugMode` call `gpio_reset_pin`/`gpio_set_direction` on them unconditionally, and `docs/hardware.md` has no v2 pin map yet. Revisit when the v2 map exists (the driver must skip NC pins first). GPIO 3 (JTAG source strap) stays accepted.

## 2026-10-18: Deinit exceptions after P2.13e
SD card, battery ADC and LED now have `deinit()` and are in the sleep path (`power.md`, Deinit and init order). The P2.4 "every component has init/deinit" rule is met except for three platform services that stay up on purpose: Settings (NVS stays initialised, nothing to release), power management (the PM lock must exist to let light sleep happen) and the `www` LittleFS mount (read-only, no task or ISR, re-mounting on every wake costs more than it saves). Any new component must have `deinit()`; these three are the only exceptions, and CLAUDE.md's wording stands with that list. Battery is released around the light sleep rather than in STOPPING because the SLEEPING state reads the voltage every pass. Unverified on hardware: SD unmount/remount and ADC re-init across a real sleep/wake cycle.

## 2026-10-18: Non-breaking API cleanup (P2.11, NB1-NB5, NB7, NB8)
Implements the non-breaking items of the P2.7 API review. Contract details are in `docs/api.md`.
- **One error body.** `{"status":"error","reason","code"}` with `Content-Type: application/json` from every layer: the async server (429, 503), the handlers and the middleware. One IDF-free header, `components/async_web_server/include/http_error.hpp`, holds status lines, default codes and the body builder; `AsyncWebServer::sendError()` puts it on the wire. P2.10 auth reuses it for 401, 403 and 429 (own `Retry-After` argument). Replaces the `{"error":...}` shape and the invalid `503 Busy` status lines. RFC 7807 stays rejected (flash and frontend churn); `code` is additive, `reason` is unchanged for `api.ts`.
- **Status table in one place.** `http_error::statusForError`: 504 only for CAN/ECU waits, 503 plus `Retry-After: 1` for a busy local lock, queue or SD operation or a stopped component, 502 for an ECU answer that cannot be used (`POST /req/vin`), 500 for out of memory. Changes visible to scripts: PID map lock timeouts 504 -> 503, `PUT /pid_def` with OBD2 stopped 500 -> 503, recursive delete deadline 504 -> 503, no valid VIN 500 -> 502.
- **Settings validation failures stay 400.** The review's checklist notes that `POST /settings` uses 400 where the 400/422 rule (unparseable vs parseable but invalid) would say 422. NB3 does not ask to change it, the settings page (P3, BR3) will reshape the endpoint anyway, and 400 is documented, so it stays 400 until BR3. Not changed here.
- **Wildcards removed** from `/dtc`, `/req/dtc` and `/req/auto_poll`; the route table is the `API_ROUTES` X-macro in `main/include/api_routes.hpp`, with a host test that only the four path-parameter routes may contain `*`.
- **`api_version`** (integer, `API_VERSION` in `utilities.h`, 1) in `GET /system`. Rule: additive changes inside `/api/v1` need no bump, breaking ones bump it and ship with the frontend. `Cache-Control: no-store` on all JSON. The optional `Cache-Control`/ETag for `GET /` is not done.
- **Stricter queries.** `auto_poll` accepts only `true|false|1|0`; DTC `mode` rejects negatives; `GET /dtc` and `POST /req/dtc` reject unknown or repeated keys. Scripts that sent `auto_poll=yes` or `mode=-1` now get 400.
- **Bounded `GET /sd_card/tree`.** Defaults `depth=5`, `limit=256`, `offset=0`; `limit` max 512; reply has `truncated`. A directory below `depth` is listed unopened (`truncated:true`) instead of the old 500. The reply is now capped at 256 entries by default, and the frontend does not yet show `truncated`.

## 2026-10-18: BOOT button driver and Host/Origin guard (P2.10a, P2.10b)
- **Button mechanism: GPIO interrupt plus one task, no polling timer.** Both-edge interrupt notifies a task, which waits 30 ms, samples once and sleeps again. Idle cost is zero wake-ups (a 20 ms poll timer would wake the CPU 50 times a second for the whole awake time). Hold detection uses the task's wait timeout. The ISR service is shared (`gpio_install_isr_service` may already exist) and is never uninstalled. A button already down at init is ignored until released once, so a held BOOT cannot open the claim window. The component is C (`button.c`, `button.h`) with an IDF-free `button_logic.h` for host tests. The hook is a mutex-guarded {fn,arg} that the task holds during the call (`HookCell` is C++ and lives in `can_driver`); `set` waits for a running call. Lifetime follows the web server (`setup_web_server` / `stop_web_server`), so no supervisor change.
- **Hold gesture for recovery: 10 s.** The decision named "the same button" without a duration. 10 s avoids accidental triggers and is still easy at the device.
- **Guard placement.** `AsyncWebServer::Config::request_filter` runs in the httpd task for every REST request before the rate limit and the queue; `/ws` calls the same Host/Origin check in its upgrade handler. Rejected requests do not use a worker. Statuses: 403 `BAD_HOST`, 403 `BAD_ORIGIN`, 415 `BAD_CONTENT_TYPE` (new status line and default code in `http_error.hpp`).
- **Allowed hosts** are read per request from the Wi-Fi netifs (`getApIP()`, `getStaIP()`), `0.0.0.0` counts as unset, port is none or 80. A request without `Origin` passes (non-browser clients, same-origin GET); the Host check alone covers rebinding. Content-Type is checked only when a body is present, because the frontend's bodyless `POST` (new directory) sends `text/plain` with length 0.

## 2026-10-18: Access control as built (P2.10c)
Implements the 2026-10-18 access-control decision. Choices that the decision left open:
- **PBKDF2 cost: 5000 iterations, unmeasured.** `mbedtls_pkcs5_pbkdf2_hmac_ext` (SHA-256), checked on the host against Python `hashlib` for the same inputs. No board was flashed, so the S3 time is an estimate (about 20 to 50 us per HMAC iteration including the PSA layer, so 100 to 250 ms). The first derivation logs `PIN derivation: N iterations, T ms`; adjust `auth_service::kPbkdf2Iterations` from that line (stored per record, so old PINs keep working). Honest limit: a 6-digit PIN has 10^6 values, so the hash only slows an offline attack on a flash dump down to minutes on a PC. It is not a defence against someone who can read the flash.
- **One blob in NVS** (`auth/pin`: version, iterations, salt, hash) so a power cut cannot pair a new salt with an old hash. An unreadable or corrupt record is not "unclaimed" (that would let the next BOOT press claim a device whose PIN was merely lost to a read error): it is `unavailable`, gated routes answer 503, and the 10 s BOOT hold clears it.
- **Backoff:** `min(2^(N-1), 900)` s after the Nth consecutive wrong PIN, global, RAM only. 900 s cap because the BOOT-hold recovery exists; at the cap an online brute force of 10^6 PINs takes years. Attempts during the wait are refused without a key derivation and do not extend the wait. Format errors in the PIN field count (no oracle); a missing or non-string field does not (client bug, 422).
- **Recovery gesture:** hold BOOT 10 s (see the button entry above). It also clears the sessions and resets the login backoff. It works while the device is awake and the web server is up; physical access is the trust anchor, same as the claim.
- **Claim logs the caller in** and returns a token (delivered by the claim poll since d2, see below). The press-then-post window of the first version is replaced by the two-step claim in d2.
- **Session overflow:** the fifth login replaces the session idle longest instead of failing, so a forgotten browser tab cannot lock the owner out. An attacker without the PIN cannot create sessions, so this is not a lever for denial of service.
- **`PUT /auth/pin` and `POST /auth/logout` are gated** (need a session) and `PUT /auth/pin` also needs the old PIN; a wrong old PIN counts as a failed login. The decision's list did not name them.
- **Error codes:** 401 `UNAUTHORIZED` (no or dead session), 401 `BAD_PIN` (with `Retry-After`), 429 `LOGIN_BACKOFF`, 403 `NOT_CLAIMED` (gated route or login on an unclaimed device: 403 rather than 401, because a login cannot succeed yet), 403 `BUTTON_REQUIRED`, 409 `ALREADY_CLAIMED`, 422 `BAD_PIN_FORMAT`, 503 `AUTH_UNAVAILABLE`, 500 `AUTH_INTERNAL`.
- **Order of checks:** Host/Origin, Content-Type, session check, global rate limit, handler. The decision lists rate limit after auth; that is what this does (rate limit is in `queue_request`, after the filter). Bodies over 1 KiB are judged in the worker (`route_shim`) because httpd reads and discards an unread body in the HTTP task after a handler returns, and a hostile 4 MiB upload must not stall the task that serves every socket; for those the rate limit runs before the check.
- **`api_version` is 2.** Gating existing routes (settings, SD files, `pid_def` writes, reboot, copy, `clear_dtc`) is a breaking change for any client that does not log in. The frontend needs P2.10d to use them.
- **NVS erase unclaims.** A factory reset that erases NVS also removes the PIN record, so the device is unclaimed and needs a BOOT press to claim: fails safe.
- **Residual risk (unchanged from the decision):** open AP and plain HTTP, so PIN and token are readable by anyone in radio range. Anyone with physical access can clear the PIN by holding BOOT.

## 2026-10-18: clear_dtc loses its confirm token (P2.10c-cleardtc)
Decided by the user: `POST /req/clear_dtc` is protected by the Bearer session (`gated` in `API_ROUTES`) and nothing else. The one-shot 409 `confirm_required` challenge, `ConfirmToken` (`confirm_token.hpp`) and its host test are removed; the call sends mode 0x04 at once. A leftover `?token=` is ignored, so the current frontend does not get a 400, but it also no longer gets a 409 first: without a session it gets `401`, with one the first call clears the codes. The confirmation is the frontend's own dialog (client side only). Consequence: any client holding a session can clear codes with one request; a script that relied on the 409 to be safe must now ask the user itself. The REST contract no longer has a non-error 4xx.

## 2026-10-18: Security review decisions (P2.10d)
Decided by the user after the P2.10c security review. Each item is its own commit.
- **d1, owner lockout:** a BOOT press the auth core has not seen yet resets the login backoff (checked on every login, PIN change and `GET /auth`). Otherwise the global counter works as before. Without this, anyone on the open AP could keep the owner locked out for up to 15 min by failing logins; with it, physical presence beats the remote attacker.
- **d2, two-step claim (option A):** the first PIN is posted to a single pending slot; a BOOT press after the post and within 60 s commits it; a second post cancels both. Replaces "press first, then post within 60 s", where a bystander could press BOOT and claim the open AP before the owner. The hash is derived at post time (never under the lock, never for a conflict, a claimed device or a bad PIN). The commit happens lazily, in whichever auth call looks at the claim first (`GET /auth`, a claim poll or a post), so the button driver needs no extra callback; if nobody asks, the slot simply expires. Delivery of the token is by polling `GET /auth?claim_id=` (long polling would hold one of the 6 workers per waiting client for up to 60 s). The id is a 128-bit random secret; the first poll that sees the commit returns the token once. `GET /auth` shows only `unclaimed` / `pending` / `claimed` / `unavailable` and a global countdown, no per-client data. Residual: a hostile client can keep forcing conflicts and so deny the claim while the device is unclaimed; it cannot claim. Recovery by BOOT hold clears a pending claim and needs a fresh post and press. This also removes the doc bug that said the hold resets a "used-press marker" (there is no such marker any more).
- **d3, low findings:** the failed-login count lives in `RTC_NOINIT` next to a magic word (same pattern as the supervisor's error counter), is capped at 32 and restored on every `auth_service::start()`, so a crash or a sleep/wake no longer clears the penalty; only the count survives, the wait restarts from boot. It is cleared by a correct PIN, a new BOOT press, recovery and a PIN change. `onHold` logs a warning when it cannot get the operation mutex (the user holds again). The `stop()` versus hold-hook race is closed: `s_up` drops first, a late `onHold` returns without touching the core, and the operation mutex is a static object that is never deleted, so a waiting recovery cannot use freed memory.
- **d4, accepted risks and AP warning:** flash and NVS encryption stay off (user declined): anyone with the board can read the PIN hash and Wi-Fi passwords from flash, and the 6-digit PIN is brute-forced offline in minutes. The open AP stays a supported setting (the user may also choose it later); the real-world risk is judged low. To make the risk visible, `GET /auth` carries `ap_open` (additive, so `api_version` stays 2), derived from the applied Wi-Fi config (`WIFI::isApOpen()`), for a frontend warning that traffic, the PIN and the token are readable by anyone in range.

## 2026-10-18: Backend-first bounded Wi-Fi scan (P3.W1/W2)
User-approved: asynchronous scanning, 20 output records, 5 s deadline, 10 s start cooldown and 30 s result/failure cache. Authenticated `POST /api/v1/wifi/scan` admits an attempt with 202; GET reads its status/results. Busy/down/timeout is 503, cooldown 429, allocation failure 500. The frontend is explicitly deferred, overriding the usual same-commit frontend rule for this additive backend contract; `api_version` remains 2.

The AP remains running: AP-only scanning temporarily enables AP+STA and restores AP without writing config/NVS; no explicit Wi-Fi stop/start is used for scanning. Active scans exclude reconnect/fallback. Blocking scans were rejected because they occupy HTTP workers and complicate shutdown. A single short-lived worker waits for SDK completion or cancellation, uses a fixed SDK output array, and exits; no scan polling timer runs. A separate one-shot timer retries deferred reconnect work only when needed. A missing completion or cleanup/restoration error quarantines new scans until full deinit/init; silently reusing an unretired completion is rejected. Driver deinit and an event-loop barrier retire old events before reinit.

**Explicitly approved memory boundary:** application-owned result snapshots, output buffers and serialization are capped at 20 records; SDK driver-internal dynamic allocations are opaque and are not hard-capped. The public scan config has no allocation/result-list cap. `esp_wifi_scan_get_ap_records` caps output and frees the driver list afterward; it does not bound its peak size during discovery. Firmware clears the list on empty/error/cancellation paths when scan completion/stop permits it. An SDK stop failure leaves cleanup to driver stop/deinit rather than clearing a possibly active scan. Dense-RF heap measurements can detect regressions but cannot prove an undocumented hard allocation bound.

Source verification used official online ESP-IDF release-v6.1 docs and v6.1 tagged public headers, not denied installed SDK source:
- [Wi-Fi API](https://docs.espressif.com/projects/esp-idf/en/release-v6.1/esp32s3/api-reference/network/esp_wifi.html): async `scan_start`, dynamically allocated results, `scan_stop`, RSSI-sorted capped `scan_get_ap_records`, `clear_ap_list`.
- [Station scan scenarios](https://docs.espressif.com/projects/esp-idf/en/release-v6.1/esp32s3/api-guides/wifi-driver/station-scenarios.html): scanning requires STA/AP+STA; connection scans do not emit scan-done events; concurrent scans must be avoided; background scans return home for 30 ms.
- [v6.1 scan config](https://github.com/espressif/esp-idf/blob/v6.1/components/esp_wifi/include/esp_wifi_types_generic.h#L248-L260): timing/channel filters, no driver allocation bound.
- [v6.1 timer API](https://github.com/espressif/esp-idf/blob/v6.1/components/esp_timer/include/esp_timer.h): `esp_timer_stop_blocking` guarantees callback quiescence on successful task-context return.
- [v6.1 default Wi-Fi teardown](https://github.com/espressif/esp-idf/blob/v6.1/components/esp_wifi/src/wifi_default.c): `esp_netif_destroy_default_wifi` clears the default netif bindings/handlers and destroys the attached interface driver, unlike plain `esp_netif_destroy`. Teardown now uses the matching helper.

Not yet hardware-verified: AP continuity during live mode transitions, scan/stop timing, dense-RF internal heap pressure, worker stack headroom, repeated scans and scan-versus-sleep teardown. No hard real-time bound is claimed for SDK calls or scheduler latency.

## 2026-10-18: Development login bypass (P2.10f)
Decided by the user, so the frontend can be developed without a token. Constraints: compile time only (`CONFIG_SNIFFER_AUTH_DEV_BYPASS`, Kconfig bool, default n, not in any committed config); no runtime switch of any kind, and with the option off the code is not compiled (`#if`, plus a host test that pins `auth_dev::kBypass == false` and that the core refuses a missing token). When on, `auth_service::requireAdmin` returns Ok for every gated route; the Host/Origin and Content-Type guards, the claim/login/PIN routes and the open routes are unchanged. It is loud: a warning at boot and at most once a minute while requests pass, `dev_bypass:true` and `authenticated:true` in `GET /auth`. Guards against shipping it: `CONFIG_SNIFFER_RELEASE_BUILD` (Kconfig, default n; set it for every image that leaves the bench) turns the combination into a `#error` in `auth_dev.hpp`, and `tools/ci.sh` fails if `CONFIG_SNIFFER_AUTH_DEV_BYPASS=y` appears in `sw/firmware/sdkconfig` or `sdkconfig.defaults*`. `sw/firmware/sdkconfig` is tracked, so the bypass is built from an untracked overlay and its own build directory instead of `menuconfig` (docs/architecture.md, Development login bypass). Not added to `GET /system`.
