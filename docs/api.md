# API: firmware ↔ frontend

This is the contract between `sw/firmware` and `sw/frontend`. A change here lands in both sides and this doc in the same commit.

Source of truth in the firmware: the route table `api_routes` in `sw/firmware/main/src/webserver.cpp` (handlers), `sw/firmware/main/src/middleware.cpp` (response bodies and status mapping). Frontend callers (the table names the function) are in `sw/frontend/src/lib/canStore.svelte.ts`, `lib/api.ts` and `lib/components/`.

## Conventions
- Server: port 80, host `can-sniffer.local` (mDNS) or the device IP. No TLS: the default AP is open, so the PIN and the session token cross the air in clear text (accepted risk, `decisions.md` 2026-10-18). Routes marked **gated** need a login (see Authentication); everything else is open.
- Base path: `/api/v1`. The frontend page itself is `GET /`.
- Format: JSON, `Content-Type: application/json`, unless noted. Numbers that are NaN or infinite are serialized by cJSON as `null`.
- Requests are queued to 6 worker tasks. The server rate limit is global, not per client: more than 50 requests in a one-second window get `429`.
- Request body limits: 2048 bytes for JSON bodies, except `PUT /pid_def` (64 KiB), the two PID file calls (256 bytes), and SD upload (4 MiB). JSON bodies need a `Content-Length` header and must arrive within 5 s in total (`PUT /pid_def`: 20 s), else 400 `Incomplete request body`; chunked bodies are rejected with 400.
- JSON responses, errors included, carry `Cache-Control: no-store`.

### Host, Origin and Content-Type guard
Checked for every REST request in the HTTP server task, before the rate limit and before a worker is used (`request_filter` in `webserver.cpp`; logic in `main/include/host_guard.hpp`, host-tested). The WebSocket upgrade on `/ws` gets the Host and Origin check as well.
- `Host` must be `can-sniffer.local`, the AP address or the STA address (as the device reports them now; `0.0.0.0` never matches), optionally with `:80`, case-insensitive for the name. A missing, other or over-long (64 B) value gets `403` `BAD_HOST`. This stops DNS rebinding.
- `Origin`, when the client sends one, must be `http://` plus one of those hosts. Anything else (`null`, https, another host or port, a path) or an over-long (96 B) value gets `403` `BAD_ORIGIN`. This stops cross-site requests and WebSocket hijacking. Clients that send no `Origin` (curl, scripts) pass this check.
- A `POST`, `PUT` or `PATCH` that carries a body (`Content-Length` above 0) needs `Content-Type: application/json` (optionally `; charset=utf-8`), or `application/octet-stream` on `PUT /sd_card/file/<path>`. Anything else, or a missing header, gets `415` `BAD_CONTENT_TYPE`. A request without a body is not checked. This closes the HTML-form and `text/plain` cross-site paths.
- Developing the frontend through a dev-server proxy (`bun run dev`) needs the proxy to send an allowed `Host` and `Origin`, or the guard answers 403.

### Authentication
Decision and threat model: `decisions.md`, 2026-10-18. A 6-digit PIN protects the **gated** routes (marked in the table below). It stops cross-site forgery, DNS rebinding and casual users; it does not stop someone who can sniff the open AP, who reads the PIN and the token. The WebSocket and the dashboard reads stay open. Order of checks for a REST request: Host/Origin guard, Content-Type, session check (gated routes only), the global rate limit, the handler. Bodies over 1 KiB are checked in the worker instead of the HTTP task so that a hostile upload is never read by the task that serves every socket.

- **Session token.** `Authorization: Bearer <32 hex>` header, no cookie. 128 random bits from the hardware RNG, kept in RAM only (lost on reboot and on every sleep, because the web server stops), at most 4 sessions (a fifth login replaces the one idle longest), 30 min idle and 12 h absolute expiry. Any request that passes the check, `GET /auth` included, restarts the idle timer. Missing, malformed, unknown and expired tokens all give the same `401` `UNAUTHORIZED`.
- **PIN.** Exactly 6 ASCII digits. Stored as one NVS blob (namespace `auth`, key `pin`): PBKDF2-HMAC-SHA256, 16-byte random salt, 5000 iterations (`auth_service::kPbkdf2Iterations`, stored with the record), constant-time compare. The PIN and tokens are never logged.
- **Claim, in two steps.** A device nobody has claimed has no PIN. Step 1: `POST /auth/claim {"pin"}` derives the hash and parks it in the one pending slot, answered `202` with a `claim_id`. Step 2: someone presses BOOT (GPIO0) on the device **after** the post and within 60 s of it; that press commits the parked PIN. The client learns the result by polling `GET /auth?claim_id=<id>` about once a second; the poll that sees the press does the commit and returns the session token once. A press made before the post, or later than 60 s after it, does nothing. This stops a bystander on the open AP from claiming the device by pressing BOOT first: the PIN in the slot is the poster's. A second `POST /auth/claim` while one is pending **cancels both** (`409` `CLAIM_CONFLICT`, the first client's poll says `conflict`); both clients start over. Anyone on the AP can force that conflict, so a hostile client can delay a claim but never take it. A claimed device answers `409` `ALREADY_CLAIMED`.
- **Claim states for a client** (`GET /auth`): `state` is `unclaimed` (nothing parked; show the PIN form), `pending` (a claim waits for the press; show "press BOOT now", `claim_expires_in_s` counts down; it is global, the same for every client), `claimed` or `unavailable`. The per-client result is `claim.result` when `claim_id` is sent: `pending` (with `expires_in_s`), `committed` (with `token`, `idle_timeout_s`, `max_age_s`, delivered in the first poll that sees it only; a lost response means log in with the PIN), `expired` (no press in time), `conflict` (another claim arrived), `failed` (the press came but the record could not be stored; nothing changed, retry) and `unknown` (id never issued, malformed, or forgotten after 5 min). `expired`, `conflict`, `failed` and `unknown` are final: post again.
- **Recovery.** Hold BOOT for 10 s while the device is awake: the PIN, all sessions and the login backoff are cleared and the device is unclaimed again (a claim needs a new post and a new press). Also the way out of `AUTH_UNAVAILABLE`.
- **Backoff.** One global counter of wrong PINs, not per client (an open AP lets a client change address freely): after the Nth wrong PIN in a row login is refused for min(2^(N-1), 900) s, answered `429` `LOGIN_BACKOFF` with `Retry-After`. Attempts during the wait do not run the key derivation and do not extend it. A correct PIN resets it, and so does a BOOT press the device has not seen before (the owner standing at the device is never locked out by an attacker's failures). It blocks `POST /auth/login` and the old-PIN check of `PUT /auth/pin` only; existing sessions, claim and every other route are never affected. The failure count is kept in RTC memory, so a crash, a reboot or a sleep/wake does not shed it (the wait itself restarts from the next start; RTC memory is undefined after a power loss, where the count starts at 0).
- **Fail closed.** If NVS cannot be read or the record is corrupt, gated routes answer `503` `AUTH_UNAVAILABLE` and the rest of the device keeps running. If the BOOT button driver failed to start, nobody can claim (`403` `BUTTON_REQUIRED`).

### Versioning
- `GET /api/v1/system` returns `api_version` (integer, `API_VERSION` in `utilities.h`, currently 3) next to `app_version` (`APP_VERSION_STRING` from `APP_VERSION_MAJOR/MINOR/PATCH`, `"1.2.4"` when checked). `app_version` is the firmware release, `api_version` is the contract.
- Inside `/api/v1` only additive changes are allowed without a bump: new routes, new response fields, new optional parameters, new enum values that clients ignore. Clients must ignore fields they do not know. Anything else (rename, removed field, changed status or type) is breaking: it bumps `api_version` and lands with the matching frontend in the same commit.
- That is acceptable only while the frontend ships in the same image as the firmware. If the frontend can be updated separately (open decision D9), it must read `api_version` on connect and show a firmware/web mismatch notice, and breaking changes then need `/api/v2` routes. The server has 48 handler slots and uses 39 (38 REST routes plus `/ws`), so a side-by-side `/api/v2` fits only for a few routes.
- WebSocket: no version byte. New frame types use unused type bytes; the size of an existing frame never changes. The protocol version is the `api_version` fetched over REST when the socket opens.

### Error body
Every error, from every layer (async server, handlers, middleware), has one shape and `Content-Type: application/json`:
`{"status":"error","reason":"<human text>","code":"<STABLE_TOKEN>"}`. `reason` is for people and may change. `code` is for clients and stays stable: a status default (`BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `REQUEST_TIMEOUT`, `CONFLICT`, `TOO_LARGE`, `UNPROCESSABLE`, `RATE_LIMITED`, `INTERNAL`, `BAD_GATEWAY`, `BUSY`, `GATEWAY_TIMEOUT`, `UNSUPPORTED_MEDIA_TYPE`), a specific token (`BAD_JSON`, `BAD_PATH`, `SHUTTING_DOWN`, `BAD_HOST`, `BAD_ORIGIN`, `BAD_CONTENT_TYPE`, and the auth codes below) or an `esp_err_to_name` string such as `ESP_ERR_NOT_FOUND`. `429` and `503` carry `Retry-After: 1`. Status lines use standard reason phrases (`503 Service Unavailable`). The frontend (`lib/api.ts`) treats a non-2xx status or a body with `"status":"error"` as an error and shows `reason`.
- There is no non-error 4xx: every 4xx and 5xx body is this error shape.
- Bulk calls answer 200 with `"status":"partial_success"` (see `POST /pid_def`, `POST /req/dtc`).
- Source: `components/async_web_server/include/http_error.hpp` (status lines, default codes, body builder; host-tested) and `AsyncWebServer::sendError`. The middleware builds the same fields in `json_error_body`; the code is filled from the HTTP status when the body is sent.
- A handler that gets no body from the middleware (allocation failed) answers with the status default `reason` and `code`.
- Unknown paths and unsupported methods are answered by the ESP-IDF server itself: `404`, `405`, `414`, `431` and so on, with a `text/html` plain message, not this JSON. Clients should not rely on a JSON body for those.

Status mapping (`http_error::statusForError`, host-tested), where a route says "mapped": `ESP_ERR_INVALID_ARG` → 400 (or the route's own status: 422 for a body that parsed but is invalid, 404 for a missing item), `ESP_ERR_NOT_FOUND` → 404, `ESP_ERR_TIMEOUT` → 504 when a CAN/ECU wait expired and 503 when a local lock, queue or SD operation did not become free, `ESP_ERR_INVALID_STATE` (component not running) and `ESP_ERR_INVALID_SIZE` (capacity) → 503, `ESP_ERR_INVALID_RESPONSE` (an ECU answered, the answer is unusable) → 502, everything else (including out of memory) → 500. 504 therefore means "the bus did not answer"; 503 means "this device is busy or not running, retry" and carries `Retry-After: 1`. For SD routes a timeout acquiring the SD lock (1 s) is reported as 503 `"SD card busy"`.

### Long-running routes
There are 6 worker tasks and 12 queue slots; a request that holds a worker for seconds leaves fewer for the rest. A client should not fire these in parallel. Worst cases from the code:
- `POST /req/dtc`: each mode waits up to 500 ms for an answer, with retries and multi-frame reassembly on top; without `mode` it asks modes 3, 7 and 10 one after the other. The P2.7 review estimated a worst case of about 11 s for all three; that was read from code and has not been measured. Only one `POST /req/dtc` (any mode, or none) runs at a time so it cannot occupy several async workers; a second one gets 503 `BUSY` at once.
- `POST /req/vin` and `POST /req/clear_dtc`: up to 500 ms.
- `GET /sd_card/file/<path>`: up to 5 minutes (the SD lease is held while streaming). `PUT /sd_card/file/<path>`: 5 s without progress or 60 s in total.
- `DELETE /sd_card/file/<dir>/`: up to 30 s. `POST /sd_card/format`: seconds, depends on the card.
- `PUT /pid_def`: up to 20 s to receive the body; other JSON bodies 5 s.
- JSON pre-scan (HEAP-1): before parsing, every JSON body and the PID file are scanned. More than 8192 values, more values than a third of the byte count plus 16, or nesting deeper than 32 gives 400 `BAD_JSON`. Parsing is also refused with 503 when the estimated parse cost (64 B per value plus the text) would leave less than 32 KiB free heap. Object keys do not count as values.
- Any SD route waits up to 1 s for the SD lock, then answers 503 `SD card busy`.

The `POST /pid_def` body limit (2048 bytes) is much smaller than `PUT /pid_def` (64 KiB): pasting about ten full PID objects into POST gets 413 `TOO_LARGE`. Use PUT for bulk changes.

### Path parameters
- `<pid>` is a decimal integer 0–65535 (`strtol` base 10). Anything else gives 400. PIDs are keys in one map, shared by all modes (`pid-config.md`).
- `<path>` (SD routes) is relative to the SD mount (`/sdcard`). It is percent-decoded. Separators must be a literal `/` (`%2F` is rejected). Rejected: empty or `.` or `..` components, `//`, control characters, `\`, `?`, `#`, `"`, and anything that does not fit in 512 bytes. A single trailing `/` is meaningful (directory).

## REST endpoints
39 routes are registered in `api_routes`: `GET /` and 38 under `/api/v1`. Routes are registered as exact paths (the query string is not part of the match), so `GET /api/v1/dtcs` or `PATCH /api/v1/obd2x` get the server's 404. Four patterns end in `/*` because the handler validates the remainder as a path parameter: `/api/v1/pid_def/*` and `/api/v1/pid_data/*` (`<pid>`; anything else, such as `/pid_def/foo`, gets 400), `/api/v1/sd_card/tree/*` and `/api/v1/sd_card/file/*` (`<path>`). The route table is `API_ROUTES` in `main/include/api_routes.hpp`, checked by a host test. In the table "Q" is the query string, "B" is the request body. Frontend caller `–` means no caller exists in the frontend today.

### Wi-Fi scan lifecycle
- Both routes use the normal Host/Origin, Bearer-session and global rate-limit checks, followed by component-level admission. POST consumes the global cooldown only when a task is admitted; unsuccessful admission does not extend it. At most one scan runs, with a 10 s minimum interval between starts. `scan_id` identifies the latest admitted attempt, not a per-client job. POST admission does not guarantee success; poll GET about once a second.
- Results are the strongest 20 AP records, RSSI descending, without SSID de-duplication. `truncated` means more driver records existed than were returned. RSSI is dBm; `auth_mode` is the numeric IDF `wifi_auth_mode_t`, not the restricted settings enum. No BSSID or passwords are returned.
- `ssid` is bounded to 32 bytes of valid UTF-8: malformed UTF-8 and ASCII controls are replaced with `?`; JSON quotes/backslashes are escaped by cJSON. `ssid_hex` is lowercase hex of the driver's SSID bytes up to its first NUL, at most 64 characters. Embedded-NUL SSIDs cannot be represented losslessly by the SDK's NUL-terminated record. Manual SSID entry remains necessary.
- Scan deadline is 5 s from admission. Completion after that time is a failure, not a partial success. Cancellation may take a further 500 ms to drain the completion event, plus scheduling/SDK-call latency; this is not a hard real-time API-call guarantee. Failed scans return normal error JSON (no networks), 503 except SDK/application OOM (500).
- The latest completed result or failure expires after 30 s without refreshing on reads; the next GET becomes `idle` with an empty array. `age_ms` is the age of a successful result, otherwise 0. Starting a new scan discards the previous snapshot; deinit clears it. Empty successful scans return `complete` and `networks:[]`.
- The AP is not explicitly stopped for scanning. AP-only mode temporarily enables STA radio functionality via AP+STA, without changing persisted settings, and restores AP after cleanup. STA reconnect/fallback is deferred while a scan is active. Scanning is refused during startup/STA connection. Off-channel scanning can still delay HTTP/WebSocket traffic or disconnect clients; continuity needs hardware verification.
- Missing cancellation completion, a failed stop, cleanup failure or mode-restoration failure quarantines new scans until a full Wi-Fi deinit/init. Stop/deinit close admission, cancel and wait up to 2.5 s for the scan worker; drain failures propagate as errors rather than freeing beneath it. SDK calls and mutex acquisition can add latency.
- **Memory boundary approved by the user:** application snapshots, SDK output buffer and JSON generation are capped at 20 records. The Wi-Fi driver dynamically allocates its internal discovery list, with no public hard cap. Output trimming does not bound that internal allocation. See `decisions.md` for the accepted limitation and validation scope.

### Settings validation
Settings rules (rejected with 400, never clamped): `ssid` 1..32 bytes, `sta_ssid` 0..32 bytes; `password` and `sta_password` empty or 8..63 bytes; `password` must be empty when `auth_mode` is 0 (open) and non-empty otherwise; `auth_mode` and `sta_auth_mode` one of 0 open, 2 WPA, 3 WPA2, 4 WPA/WPA2, 6 WPA3, 7 WPA2/WPA3; `mode` 1..3; `channel` 1..13; `max_connections` 1..10. CAN: `bitrate` one of the four values; `rs_mode` 0 or 1; `tx_pin, rx_pin, lbk_pin, rs_pin` must be distinct usable GPIOs (1..18, 21, 38..42, 47, 48; not BOOT 0, USB 19/20, flash and PSRAM 26..37, console 43/44, input-only 46) and not an SD or LED pin of the board; `mfilter_cfg.id` and `mask` fit 11 bits (29 bits with `is_ext`). `pid_def_path` and `dtc_desc_path` start with `/sdcard/`, have no `..` path component and are at most 255 bytes. Numbers must be JSON integers.

### PIDDef (responses of `GET /pid_def`)
`{pid, mode, id, length, name, unit, description, minValue, maxValue, priority, update_interval_ms, color, icon, formula}`

The request and file format uses different names for the same fields: `desc`, `minV`, `maxV`, `interval` (and `len` as an alias of `length`). See `pid-config.md`. The frontend converts in `serializePidDefinition`.

### PIDData (responses of `GET /pid_data`)
`{id, pid, value, lastUpdated, isSupported, isValid, update_interval_ms}`. `id` is the CAN ID of the ECU that answered (or the configured request ID before support is known). `lastUpdated` is milliseconds since boot. `value` is the formula result, `null` when it is NaN.

## WebSocket
- Path: `/ws` (plain `ws://`, GET upgrade). Binary frames only. All multi-byte values are little-endian.
- There is no per-client state. The flags below are global. The frontend sends one ping every 3 s, never while a pong is outstanding, and reconnects when no pong arrives within 6 s. It resets its reconnect backoff on the first pong, and gives up a socket that is not open within 5 s.
- On connect the server starts the 1 Hz CAN status stream. The stream stops when the last client closes.

| Type | Direction | Payload | Rate |
|---|---|---|---|
| `0xA0` start PID stream | client → server | 1 byte `0xA0`. Enables PID packets for all clients | on demand |
| `0xA1` stop PID stream | client → server | 1 byte `0xA1` | on demand |
| `0xA2` ping | client → server | 1 byte `0xA2` | frontend: every 2 s |
| `0xA3` pong | server → all clients | 1 byte `0xA3`, reply to a ping | per ping |
| `0x02` PID update | server → all clients, only after `0xA0` | 20 bytes: `[0]=0x02`, `[1]=18` (payload length), `[2..5]` uint32 `pid`, `[6..9]` float32 value, `[10..13]` uint32 `lastUpdated` (ms since boot), `[14..17]` uint32 update interval ms, `[18]` isSupported (0/1), `[19]` isValid (0/1) | once per PID update, so it follows the poll rate. Not throttled |
| `0x03` CAN status | server → all clients | 12 bytes: `[0]=0x03`, `[1]=10`, `[2]` CAN state (0 not initialized, 1 bus off, 2 not connected, 3 connected), `[3..6]` float32 poll utilization 0.0–1.0, `[7..10]` float32 battery voltage in V (0 = unknown), `[11]` bus connected (0/1) | 1 Hz while at least one client is connected |

Other behaviour:
- A frame longer than 125 bytes makes the server close the socket (no allocation). Text frames are logged and ignored. Unknown command bytes are logged and ignored.
- A close frame is echoed. Whenever a socket closes, for any reason (close frame, reset, timeout), and no other WebSocket client remains, both streams are turned off.
- `0x01` (`MSG_TYPE_LOG`) is defined in `middleware.hpp` but nothing sends it.
- Up to 20 WebSocket clients are considered by a broadcast. The server allows 7 open sockets in total. When the table is full the least recently used socket is closed to make room (a socket serving an async request is never chosen), and a peer that vanishes without closing is dropped by TCP keep-alive after about 25 s, so a stale browser tab cannot lock the device out. A client must reconnect if its socket is purged.
